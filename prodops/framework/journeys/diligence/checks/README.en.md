# Checks — Canonical Definition Catalog

> **This directory contains normative and reusable definitions of Diligence Checks.**
> Checks are framework rules — not product instances.
> Finding instances generated by Checks live in `prodops/artifacts/diligence/findings/`.

## 1. Purpose

This directory serves as the central repository of canonical Check definitions for Diligence. A Check is a declarative, reproducible and verifiable rule that defines **what must be evaluated** and what result is expected.

The definitions here are normative: every agent or cycle that executes Checks must use the definitions from this catalog as the source of truth — not invent ad hoc rules during execution.

| `checks/` (this directory) | `artifacts/diligence/` |
|---|---|
| Framework definitions (normative) | Product instances (operational) |
| Rules: what to verify and how | Results: what was found |
| Stable — changes when the rule changes | Grows with each new detection |
| Consumed by all products | Specific to this product |
| Versioned with the framework | Versioned with the product operation |

## 2. Relationship between Check and Finding

A Check can generate multiple Findings over time — one per different subject where the condition is detected:

```
Check DIL-TRC-001
    ├── FND-2026-0001  (Work Item #89 — no artifact_id)
    ├── FND-2026-0002  (Work Item #94 — no artifact_id)
    └── FND-2026-0015  (Work Item #112 — no artifact_id, recurrence after correction)
```

**Fundamental rules:**

- **Check does not create Finding directly.** The cycle that executes the Check decides if the Fail result should generate a Finding, based on deduplication and context.
- **Finding references the Check via the `check_id` field** (format `DIL-CATEGORY-NNN`). `check_version` records which version of the rule was in effect at Finding creation.
- **Check Pass/Not Applicable does not generate Finding.** The result must be recorded in the cycle's execution trail, not as a Finding.
- **Check Error does not generate Finding for the original rule.** May generate a separate operational Finding about the Diligence mechanism failure — never confuse the two.

```
Check executed (by Sync, Async or manual cycle)
       ↓
result evaluated
       ↓
Pass / Not Applicable → no action on Findings
Warning → evaluate if relevant for recording
Fail → Finding protocol (deduplication → create or update)
Error → evaluate: create operational Finding about mechanism failure?
Indeterminate → escalate or record Finding with insufficient Evidence
       ↓
Deduplication using key: check_id + primary subject + condition + scope
       ↓
Existing Finding?
  ├── yes → update last_detected_at, occurrence_count, add Evidence
  └── no  → generate ID (FND-YYYY-NNNN), create file, update registry
```

## 3. Structure of catalog.yaml

The catalog lives in `catalog.yaml` in this directory. Global-level fields:

```yaml

  ...

defaults:
  finding_template: prodops/templates/diligence/finding.md
  findings_dir: prodops/artifacts/diligence/findings/

  - id: DIL-XXX-NNN
    ...
```

Each entry in `checks:` follows the complete schema documented in `model/check.md`.

## 4. ID policy

**Format:** `DIL-[PREFIX]-NNN`

- `DIL` — immutable Diligence prefix
- `[PREFIX]` — three letters identifying the primary group of the Check (see table below)
- `NNN` — three-digit sequential per prefix (001–999)

| Prefix | Group | primary_dimension |
|---|---|---|
| `CON` | Conceptual | Conceptual |
| `STR` | Structural | Structural |
| `TRC` | Traceability | Traceability |
| `OPS` | Operational | Operational |
| `TMP` | Temporal | Temporal |
| `RDY` | Readiness (category/scope) | Operational |
| `WSP` | Workspace (category/scope) | Structural |

**Rules:**
- The ID is immutable after creation — it does not change when the rule changes.
- The rule version is tracked in the `version` field of the Check.
- IDs are never reused, even after deprecation or removal of a Check.
- The prefix reflects the primary group of the Check — not necessarily the `category` of the Finding it generates.

## 5. Versioning policy

### Material change (increments `version`)

Any change that alters the Pass/Fail criterion, the applicable subject, the default severity, or the blocking policy is a material change:

- Change in `expected_condition` or `failure_condition`
- Addition or removal of subjects in `scope`
- Change of `severity_default`
- Change of `blocking` (true → false or vice versa)
- Change of `waiver_allowed`
- Change of `auto_finding` or `human_review_required`

**When making a material change:** increment `version` (integer), document what changed in `notes`, evaluate whether Findings created with the previous version are still valid under the new rule.

### Non-material change (no version increment)

- Text correction without changing criteria
- Adding examples to descriptive fields
- Improving `remediation_hint` without changing the rule
- Updating `escalation_targets` without changing logic

### Finding records the Check version

The `check_version` field in the Finding indicates which version of the rule was in effect at the time of creation. When the rule changes materially, previous Findings must be evaluated: if the new rule would make the Finding invalid, the Finding receives a `Invalid Rule` classification — it is never deleted.

## 6. Dimensions

The five canonical Diligence dimensions define the **type of consistency** that the Check verifies:

| # | Dimension | What it verifies |
|---|---|---|
| 1 | **Conceptual** | Documents use ontology, vocabulary, states, relationships and responsibilities compatible with the framework |
| 2 | **Structural** | Real structure of files, directories, indexes, links and schemas corresponds to the documented model |
| 3 | **Traceability** | It is possible to reconstruct relationships between entities; references resolve to valid destinations |
| 4 | **Operational** | Operations respect schema, state, ownership, dependencies, entry/exit criteria and evidence |
| 5 | **Temporal** | The system preserves history, trails, past decisions and does not confuse historical state with current normative instruction |

**Readiness and Workspace are categories/scopes — they are NOT additional canonical dimensions.**

- Checks with prefix `DIL-RDY-NNN` have `primary_dimension: Operational`
- Checks with prefix `DIL-WSP-NNN` have `primary_dimension: Structural`

A Check has one mandatory `primary_dimension` and can have optional `secondary_dimensions` when the verified condition touches multiple dimensions.

## 7. Categories

The category of a Check reflects the type of Finding it can generate when the result is Fail:

| Category | What it represents |
|---|---|
| **Documentation** | Normative documentation: vocabulary, terminology, classifications, references |
| **Workspace** | GitHub Workspace infrastructure: Labels, Fields, Views, Projects |
| **Work Item** | Schema, traceability, state or conformance of Work Items |
| **Artifact** | Content, state, completeness or conformance of Knowledge Space artifacts |
| **Readiness** | Transition preconditions: missing artifacts, unsatisfied criteria |
| **Governance** | Governance conformance: approvals, Waivers, entities without grounds |
| **Evidence** | Verification, resolution or approval Evidence: absent where required |
| **Backlog** | Consistency between backlogs, entry/exit criteria, hierarchy |
| **Execution Mapping** | Mapping between artifacts and Work Items, KS↔ES cardinality |

## 8. Types

The type of a Check describes the **logical mechanism** of verification:

| Type | What it does | Example |
|---|---|---|
| **Presence** | Verifies mandatory existence | "Entity file must exist at canonical path" |
| **Absence** | Verifies expected absence | "Passive Signal must not have Work Item" |
| **Validity** | Verifies that reference/value is valid | "artifact_id must reference existing artifact" |
| **Consistency** | Compares two or more sources | "Registry must be consistent with entity files" |
| **Completeness** | Verifies required fields are filled | "Active Waiver must have all required fields" |
| **Traceability** | Verifies chain of relationships | "Active Work Item must have valid artifact reference" |
| **Readiness** | Verifies advancement preconditions | "Promotion criteria must be satisfied" |
| **Freshness** | Verifies temporal validity | "Expired Waiver must not be Active" |
| **Conformance** | Verifies schema adherence | "Workspace must have declared canonical fields" |
| **Outcome** | Verifies that Evidence supports result | "Implemented Remediation must have independent verification" |

## 9. Execution modes

| Mode | When it is used | Triggered by |
|---|---|---|
| **Sync** | Within a transition or ongoing operation | diligence-sync cycle phase (Promote, Close, Attach) |
| **Async** | Outside the main transaction, proactively | diligence-async periodic scan |
| **Manual** | On explicit request | Human request, Bootstrap, audit |
| **Event-driven** | Triggered by technical or operational event | PR opened, document edited, Work Item created |
| **Scheduled** | Periodically at defined interval | Automatic scheduler |

A Check can support multiple modes — the `execution_modes` field is a list.

## 10. Results

| Result | Meaning | Generates Finding? | Blocks? |
|---|---|---|---|
| **Pass** | Condition satisfied; system conforms to rule | No | No |
| **Fail** | Confirmed violation; condition not satisfied | Yes — with Check's `severity_default` | When `blocking: true` and sufficient Evidence |
| **Warning** | Relevant condition without blocking violation | May generate Finding with Info/Low severity | Never |
| **Not Applicable** | The rule does not apply to the evaluated context | No | No |
| **Indeterminate** | Insufficient Evidence to conclude | May generate Governance Finding if recurrent | Not directly |
| **Error** | The Check could not execute correctly | May generate separate operational Finding | No |

### Rules about results

- **Indeterminate ≠ Pass.** Indeterminate means absence of sufficient evidence — it is not confirmation of conformance. Treating Indeterminate as Pass masks risk.
- **Error does NOT automatically generate Finding for the original rule.** If the Check failed to execute, one cannot conclude that the rule was violated. Error may generate an operational Finding about the Diligence mechanism failure — they are two conceptually distinct Findings.
- **Not Applicable is an explicit and valid result.** Must be recorded as Not Applicable with justification — never as absence of evaluation nor confused with Pass.
- **Warning does NOT imply Fail.** Identifies something worthy of attention without blocking violation.

## 11. Blocking policy

A Check with `blocking: true` can prevent state transitions when it returns Fail. For the block to be valid, **all** criteria below must be simultaneously satisfied:

1. `blocking: true` declared in the catalog
2. Canonical `source_of_truth` identified — the rule has documented normative basis
3. Result is **Fail** (not Warning, Indeterminate or Error)
4. Sufficient Evidence was collected to support the Fail
5. `failure_condition` documented — there is instruction on how to resolve
6. Owner or escalation target identified
7. Check does not have `severity_default: Info` — Info Checks never block

The `blocking_scope` field declares which specific transitions the Check can block (e.g., Promote, Close, Registry Update, Waiver Activation, Repair).

**Checks with `severity_default: Info` never block**, regardless of `blocking: true`.

**Waiver can suspend the block** when `waiver_allowed: true` and the Waiver satisfies all validity criteria.

## 12. Waiver policy

`waiver_allowed: true` (default when not declared) means a valid Waiver can suspend the block generated by this Check.

`waiver_allowed: false` means **no Waiver can suspend the block**. This declaration is used with extreme care — only when the condition represents structural risk that cannot be managed by temporary acceptance.

### Checks with `waiver_allowed: false` in catalog v1.0.0

| Check ID | Justification |
|---|---|
| DIL-STR-001 | Using incorrect path makes the ID untraceable by any mechanism; there is no safe way to coexist with a file at the wrong path |
| DIL-STR-003 | Duplicate ID makes traceability structurally impossible; there is no safe way to operate with active duplicate IDs |
| DIL-TRC-004 | Remediation without valid Finding has no verifiable completion criterion — it is operationally empty |
| DIL-TRC-005 | Waiver without valid Finding has no semantic meaning — there is no entity to waive |
| DIL-OPS-004 | Waiving independent verification destroys the integrity of the audit cycle |
| DIL-OPS-005 | Improperly documented Waiver is a governance violation by definition — cannot be authorized by another Waiver |
| DIL-TMP-001 | Tolerating an expired Waiver as Active is disguised automatic renewal — violates the mandatory expiration policy |

**Criterion for declaring `waiver_allowed: false`:** the condition represents irreversible loss of traceability, or the condition invalidates the very governance mechanism that would allow the Waiver.

## 13. auto_finding policy

`auto_finding: true` indicates that the cycle can create the Finding automatically when the result is Fail, without human intervention.

`auto_finding: false` indicates that Finding creation requires human review even when the result is Fail — the agent prepares the Finding but does not record it alone.

### When `auto_finding: true` is safe

- The condition is objectively verifiable by file or API inspection
- The subject is always identifiable without ambiguity
- The source_of_truth is an accessible canonical file
- False positives have low correction cost
- The rule has unambiguous Fail/Pass criteria

### When `auto_finding: false` is necessary

- Evaluation requires judgment about business intention or context
- The result can be affected by conditions the agent cannot access
- The detected condition has high false positive cost
- Vocabulary or classification requires normative interpretation
- The rule evaluates normative documents with historical nuance

---

## 14. Human review policy

`human_review_required` is independent of `auto_finding`:

| `auto_finding` | `human_review_required` | Meaning |
|---|---|---|
| `true` | `false` | Finding created automatically; proceeds to Acknowledged without review |
| `true` | `true` | Finding created automatically; requires human confirmation before Acknowledged |
| `false` | `true` | Finding prepared by agent; human review decides whether to record |
| `false` | `false` | Rare — implies agent decides not to create even without automation |

`human_review_required: true` is mandatory when:
- The condition involves vocabulary or normative classification (Conceptual)
- The block can impact product decisions (OBC promotion)
- Independent verification is a model requirement (DIL-OPS-004)
- The condition requires analysis of intention or unstructured context

## 15. Evidence

Each Check declares `evidence_required` — concrete list of what must be collected to support the result. Generic Evidence ("proof that the condition exists") is not sufficient.

### Evidence principles for Checks

- Evidence must be **minimal and sufficient** — the minimum necessary to support the conclusion
- Evidence must be **concrete** — file path, field value, command output, API result
- Evidence must be **reproducible** — another agent or human must be able to verify independently
- Evidence must include **temporal context** — when it was collected and what it represented at that moment

### Preference hierarchy

1. Command Output / API Response — reproducible, verifiable
2. File content / Document path — referenceable, stable
3. Log output — system-generated, traceable
4. Human observation — last resort with justification

## 16. Subjects

Each Check has a `subject_type` — list of entity types that the Check evaluates:

| Type | Examples |
|---|---|
| **Document** | Normative Markdown file, Diligence entity file |
| **Finding** | File FND-YYYY-NNNN.md |
| **Evidence** | File EVD-YYYY-NNNN.md |
| **Remediation** | File RMD-YYYY-NNNN.md |
| **Waiver** | File WVR-YYYY-NNNN.md |
| **Work Item** | GitHub Issue, PR |
| **Artifact** | OBC, BDD Feature, Reliability Plan, Business Signal |
| **Workspace** | GitHub Project, workspace configuration |

**Primary subject** is the main object the Check evaluates and that appears in the deduplication key. **Related subjects** may be referenced in Evidence but do not define the deduplication key.

---

## 17. Deduplication

The default deduplication key is:

```
check_id + primary_subject + condition + scope
```

This key determines whether a Fail result should create a new Finding or update an existing Finding:

- **Update** when: same key + Finding is Open/Acknowledged/In Remediation + same operational context
- **Create new** when: different subject, different cause, different scope, previous Finding Closed, rule changed materially

Each Check can declare a specific `deduplication_key` in the catalog — when declared, it takes precedence over the default. The global default is defined in `defaults.deduplication_key`.

## 19. How to add a Check

1. **Define need** — identify the normative rule that justifies the Check; locate the `source_of_truth`
2. **Determine ID** — choose prefix based on `primary_dimension` and category; use next available sequential for the prefix
3. **Define required fields** — all fields marked as required in the `model/check.md` schema must be present

**Minimum required fields:**
```yaml
- id               # DIL-XXX-NNN
- version          # integer, starts at 1
- status           # Active
- name             # readable name
- description      # complete description
- primary_dimension # one of the five canonical
- category         # from canonical list
- type             # from canonical list
- execution_modes  # list with at least one mode
- cycles           # list with at least one cycle
- phases           # list with at least one phase
- source_of_truth  # list with at least one path/reference
- expected_condition
- failure_condition
- not_applicable_condition
- severity_default
- blocking
- blocking_scope
- waiver_allowed
- auto_finding
- human_review_required
- evidence_required  # list of at least one concrete item
- subject_type       # list of at least one type
- deduplication_key
- remediation_hint
- escalation_targets
```

4. **Declare `waiver_allowed: false` only with explicit justification** — document in `notes`
5. **Submit for review** — change in `catalog.yaml` must be reviewed in a Pull Request

## 20. How to change a Check

### Non-material change (editorial)

Correct text, add examples, improve `remediation_hint` without changing the Pass/Fail criterion. Can be committed directly without incrementing `version`. Briefly document in `notes` what was corrected.

### Material change

1. Increment the `version` field (integer)
2. Document what changed in `notes` (which field changed and why)
3. Evaluate existing Findings created with the previous version:
   - If the new rule would make the Finding invalid → classify as `Invalid Rule` in the Finding
   - If the Finding is still valid under the new rule → record in the Finding trail that the rule was updated
4. Submit in Pull Request with description of the change and impact on existing Findings

## 21. How to discontinue a Check

**Never delete a Check from the catalog. Never reuse an ID.**

To discontinue:

1. Change `status` from `Active` to `Deprecated` or `Retired`
   - `Deprecated`: the Check can still be referenced but should not be executed in new cycles
   - `Retired`: the Check has been definitively retired; Findings created by it are historical
2. Add `superseded_by: DIL-XXX-NNN` if a new Check replaces this one
3. Document the reason in `notes`
4. **Do not alter the `id`** — IDs are immutable
5. **Do not remove the Check from the file** — even Retired remains in the catalog for historical reference

Findings created by Deprecated/Retired Checks remain valid with their `check_id`. If the Finding is still relevant, reclassify with the substitute Check ID if there is one (`superseded_by`).

## 22. Anti-patterns

| # | Anti-pattern | Why it is wrong |
|---|---|---|
| 1 | Creating Check without `source_of_truth` | Check without normative basis is an arbitrary rule — blocks without grounds are uncontestable |
| 2 | Reusing ID of discontinued Check | Historical Findings lose valid reference; traceability broken |
| 3 | Deleting Check from catalog | Findings referencing the Check lose valid `check_id`; audit history broken |
| 4 | Treating Indeterminate result as Pass | Indeterminate means insufficient evidence — it is not confirmation of conformance |
| 5 | Treating Error result as Fail of original rule | Error means the Check did not execute — not that the rule was violated |
| 6 | Creating Check for rule that does not exist in normative document | Checks must reflect already documented rules — not invent new rules in the catalog |
| 7 | Declaring `waiver_allowed: false` without justification | Extreme restriction must have explicit reason — indiscriminate use blocks legitimate governance |
| 8 | Creating Checks that execute other Checks | Check is a declarative rule — not an executor; execution belongs to the cycle |
| 9 | Creating Checks that create Findings directly | Check evaluates and returns result; the cycle decides to create or update Finding |
| 10 | Declaring `primary_dimension: Readiness` or `primary_dimension: Workspace` | Readiness and Workspace are categories/scopes; the five canonical dimensions are the only valid ones |
| 11 | Creating Check for hypothetical unobserved condition | Check must verify real and observable condition; hypotheses belong to Assessment |
| 12 | Using generic `evidence_required` like "proof that it exists" | Evidence must be concrete (file path, command output, field value) |
| 13 | Defining `blocking: true` for Check with `severity_default: Info` | Info Checks never block by canonical rule — the combination is contradictory |
| 14 | Creating Check that evaluates execution of another Check | Checks evaluate the work system, not the execution of the Checks themselves |
| 15 | Assigning multiple `primary_dimension` | A Check has exactly one `primary_dimension`; other dimensions go in `secondary_dimensions` |
| 16 | Creating Finding for Not Applicable result | Not Applicable is a valid and correct result — it is not a divergence |
| 17 | Making Readiness Check apply universally | Readiness Checks have trigger conditions; when the trigger does not exist, result is Not Applicable |
| 18 | Using Workspace Reconciliation as Cycle in the `cycles` field | workspace-reconciliation is a Capability invoked by the cycles; the `cycles` field only accepts diligence-sync and diligence-async |
| 19 | Creating Check without defining `not_applicable_condition` | Without explicit Not Applicable criterion, Check may be applied where it should not |
| 20 | Making `auto_finding: true` for conceptual or vocabulary Check | Conceptual Checks require human judgment about intention; `auto_finding: false` is mandatory |
| 21 | Treating severity as priority in the Check | `severity_default` describes the intrinsic impact of the condition; resolution priority depends on external context |
| 22 | Creating Check with `failure_condition` identical to the negation of `expected_condition` | `failure_condition` must describe the failure state with specificity — not just the negation of the Pass state |
| 23 | Omitting `indeterminate_condition` and `error_condition` | Without definition of these results, the evaluator does not know how to proceed in edge cases |
| 24 | Incrementing `version` for editorial change | Versioning must be reserved for material changes — incrementing for every commit dilutes the signal of rule change |

## 23. Examples

### Example 1 — Structural Check with auto_finding (DIL-STR-002)

**Scenario:** diligence-async Scan executes DIL-STR-002.

```
1. Cycle reads registry.yaml → 3 entities listed: FND-2026-0001, FND-2026-0002, FND-2026-0003
2. Cycle lists files in findings/ → 2 files: FND-2026-0001.md, FND-2026-0002.md
3. FND-2026-0003 is in registry but has no file → divergence
4. auto_finding: true → cycle creates Finding without human intervention
5. Finding DIL-STR-002 created: "FND-2026-0003 in registry without corresponding file"
6. Evidence: list of IDs in registry + list of files in findings/ (diff)
7. Result recorded in Scan cycle trail
```

**What does NOT occur:** the cycle does not automatically correct the registry during Scan. Repair is the phase that executes corrections.

---

### Example 2 — Conceptual Check with human_review (DIL-CON-001)

**Scenario:** diligence-async Scan detects possible non-canonical vocabulary.

```
1. Cycle reads normative document framework/journeys/diligence/README.md
2. DIL-CON-001 identifies reference to "Workspace Reconciliation Cycle"
3. auto_finding: false → cycle prepares Finding but does NOT record automatically
4. human_review_required: true → agent presents for human review
5. Human review confirms: "Workspace Reconciliation Cycle" is incorrect usage (should be "Capability")
6. Finding created after confirmation: "Incorrect classification of Workspace Reconciliation as Cycle"
7. Evidence: document path, section, exact excerpt with the incorrect term
```

**Human decision:** confirm or discard the prepared Finding.

---

### Example 3 — Check that can NEVER return Fail (DIL-OPS-001)

**Scenario:** diligence-async Scan evaluates Business Signal without active operation.

```
1. Cycle reads tracking-list.md
2. DIL-OPS-001 evaluates Business Signal SIG-042: no marking of active operation
3. Result: Pass (absence of Work Item is the correct state)
4. Cycle trail: "SIG-042 evaluated on 2026-07-24; passive Signal; absence of Work Item confirmed as correct"
5. No Finding created
```

**If an evaluator tried to record Fail:** this would be a violation of the N:M model — the very attempt at Fail constitutes the divergence to report (not the Signal).

---

### Example 4 — Blocking Check with waiver_allowed: false (DIL-TMP-001)

**Scenario:** Waiver WVR-2026-0001 has expires_at: 2026-07-20 and is still Active on 2026-07-24.

```
1. diligence-async Scan executes DIL-TMP-001 in periodic scan
2. Result: Fail — expires_at (2026-07-20) < current date (2026-07-24) and status = Active
3. auto_finding: true → Finding created automatically: "Waiver WVR-2026-0001 expired but still Active"
4. blocking: true, blocking_scope: [Waiver Activation, Promote] → promotion blocked
5. waiver_allowed: false → no new Waiver can suspend this block
6. Evidence: expires_at field value, current date, observed Waiver status
7. Remediation needed: update Waiver status to Expired; Finding owner notified
8. Finding returns to Acknowledged → new conscious decision required
```

**Consequence:** the owner must decide: create new Remediation or create new Waiver (WVR-2026-0002) with new justification.

## 24. Scope of the first version

### What catalog v1.0.0 covers

Catalog v1.0.0 contains 18 Checks covering:

- **Conceptual** (2 Checks): vocabulary and ontological classification in normative documents
- **Structural** (3 Checks): entity file path, registry consistency, ID uniqueness
- **Traceability** (5 Checks): Work Item references, artifact resolution, Check in Finding, Finding in Remediation, Finding in Waiver
- **Operational** (5 Checks): Signal N:M model, active operation without Work Item, Work Item closure vs. Finding, independent verification, Waiver required fields
- **Temporal** (1 Check): expired Waiver must not be Active
- **Readiness** (2 Checks, primary_dimension: Operational): conditional Reliability Plan, promotion criteria
- **Workspace** (1 Check, primary_dimension: Structural): GitHub workspace schema conformance

### What is NOT covered in this version (intentionally)

- Checks about OBC state (Draft, Refining, Committed, In Delivery, Operational) — requires complete transition mapping
- Checks about BDD Features (presence, completeness, acceptance criteria)
- Checks about Reliability Plan (content, completeness, periodic review)
- Checks about Release Trail (entries, Release evidence)
- Checks about Iteration Plan (entry/exit criteria, prioritization)
- Observability Checks (metrics, SLOs, alerts)
- Security Checks (approvals, access controls)
- Check execution automation — the catalog is declarative; execution is the responsibility of the cycles
- GitHub Project schema for Findings mirroring — representation without making Issue the source of truth

### Explicit limitations of this version

- No automatic executor exists for the declared Checks
- Finding ID generation is manual (protocol documented in `artifacts/diligence/README.md`)
- GitHub Project schema for mirroring Diligence entities is not defined
- English companion file not created for this README (addressed by this file)
