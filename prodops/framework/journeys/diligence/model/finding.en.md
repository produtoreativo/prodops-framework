# Finding — Canonical Definition

## Definition

> **A Finding is the persistent record of a divergence, absence, inconsistency risk or relevant condition detected by Diligence during evaluation of the work system.**

A Finding is not a GitHub Issue. A Finding is not a Work Item. A Finding is an artifact of the Knowledge Space with its own identity, its own state and its own historical trail. Creating Work Items to investigate or address a Finding is an operational decision — not automatic.

---

## ID format

```
FND-YYYY-NNNN
```

- `FND`: immutable prefix of the Finding entity
- `YYYY`: creation year (four digits)
- `NNNN`: four-digit sequential per year (0001–9999)

**The ID is immutable.** It does not change when the state changes. It does not depend on a GitHub Issue number. It survives tool migrations.

Examples: `FND-2026-0001`, `FND-2026-0042`, `FND-2027-0001`

| Field | Conceptual type | Cardinality | Source of truth | Who can change | Validation rules |

| `status` | enum | 1 | Finding | See state flow below | Required; transitions documented in state flow |

## Five dimensions

A Finding has ONE primary dimension and may have optional secondary dimensions. Do not create duplicate Findings just because multiple dimensions are affected — the primary dimension is the most relevant for correction.

### Conceptual

**Definition:** Divergence of concept, vocabulary, ontology, responsibility, rule, classification or intention between normative documents or between documentation and the canonical understanding of the framework.

**Examples:**
- OBC of a product describes "OBC Partitioning" as "capability" when the canonical document (`ontology.md`) defines it as "governance process"
- `glossary.md` defines "Business Signal Issue" as canonical term when `knowledge-vs-execution.md` classifies it as anti-pattern
- Normative document assigns backlog prioritization responsibility to Diligence when it belongs to the Product Owner

### Structural

**Definition:** Divergence of file, directory, link, template, schema, field, configuration, View, label or any structural element between real state and the state defined in the Canonical Specification.

**Examples:**
- Mandatory field `operation` absent from GitHub Project
- Broken link in specification document pointing to non-existent file
- Canonical label `artifact-type:local-obc` absent from repository
- OBC file does not follow canonical template (required fields absent)

### Traceability

**Definition:** Divergence of reference, relation, origin, dependency, link between Knowledge Space and Execution Space, or break in the Signal → Intent → OBC → Work Item → PR → Release chain.

**Examples:**
- Work Item #57 does not have a valid `artifact_id` — broken reference
- Business Signal #BS-042 has an identified active operation but no trackable Work Item
- OBC `credit-card` references BDD Feature that does not exist in the repository
- PR #312 does not reference any canonical Work Item

### Operational

**Definition:** Divergence of state, transition, owner, entry/exit criteria, evidence, blocking or active operation that violates the operational rules of the work system.

**Examples:**
- OBC in Operational state with Work Item still open (Close was not executed)
- Item promoted to Iteration Plan without BDD Feature Committed
- Work Item marked as Done without completion Evidence
- OBC in In Delivery state without any active implementation Work Item

### Temporal

**Definition:** Expired information, outdated snapshot, expired Waiver, expired Evidence, altered history, or confusion between current state and historical record.

**Examples:**
- Waiver WVR-2025-0003 expired 30 days ago and the Finding remains with Waived status without a new decision
- Evidence collected 180 days ago references system state that has since been altered (without `valid_until` declared)
- `tracking-list.md` contains entry with obsolete vocabulary being used as current normative instruction
- OBC shows last updated date 8 months ago but the item is marked as active In Delivery

## Categories

| Category | Description |
|---|---|
| **Artifact** | Finding about content, state, completeness or conformance of Knowledge Space artifacts (OBC, BDD Feature, Reliability Plan, etc.) |
| **Backlog** | Finding about consistency between backlogs, entry/exit criteria, prioritization or backlog hierarchy |
| **Work Item** | Finding about schema, traceability, state, owner or conformance of Work Items in the Execution Space |
| **Execution Mapping** | Finding about the mapping between artifacts and Work Items, cardinality or KS↔ES relationship |
| **Documentation** | Finding about normative documentation: vocabulary, terminology, links, references, templates |
| **Workspace** | Finding about GitHub Workspace infrastructure: Labels, Fields, Views, Projects (managed by Workspace Reconciliation) |
| **Readiness** | Finding about unsatisfied transition preconditions: missing artifacts, criteria not met before advancement |
| **Reliability** | Finding about Reliability Plans: absent when required, insufficient completeness, overdue review |
| **Observability** | Finding about observability Evidence: metrics, SLOs, dashboards, alerts referenced but absent |
| **Security** | Finding about security conformance: absent or expired controls, approvals, security reviews |
| **Release** | Finding about Release Trail: missing delivery evidence, incorrect state, broken traceability between Work Item and Release |
| **Evidence** | Finding about Evidence itself: absent where required, expiration, conflict between sources, insufficiency |
| **Governance** | Finding about governance conformance: approvals, authorizations, expired Waivers, unrecorded decisions |

## Severity

Severity describes the intrinsic impact of the found condition. **Severity is not priority.** Priority depends on context, current risk, deadline, ongoing journey, business impact, exposure and correction cost.

| Severity | Criteria |
|---|---|
| **Critical** | Can cause irreversible loss of traceability; enables unsafe delivery; invalidates canonical source of truth; allows unauthorized advancement; represents serious operational risk; requires immediate blocking |
| **High** | Significantly compromises coherence or execution; may lead to incorrect decision or delivery failure; requires priority treatment; may block promotion depending on context |
| **Medium** | Reduces quality, clarity or traceability; does not require immediate blocking; should be corrected in the normal work flow |
| **Low** | Limited impact; predominantly editorial or organizational; does not compromise decision or delivery |
| **Info** | Observation, opportunity, trend, early signal; not a mandatory violation |

**Rule:** Checks with Info result **never** block. Critical Checks do not automatically imply impossibility of Waiver — the `waiver_allowed` policy of the rule defines that.

## State flow

```
Open → Acknowledged → In Remediation → Resolved → Verified → Closed
                    ↘
                     Waived (Finding remains visible and trackable)
                      │
                      └──→ (Waiver expires or is revoked) → Acknowledged
```

| State | Meaning | Who can transition |
|---|---|---|
| **Open** | Detected; not yet formally acknowledged | Diligence (automatic or manual creation) |
| **Acknowledged** | Acknowledged; cause and impact confirmed; awaiting Remediation | owner or Diligence |
| **In Remediation** | Remediation in progress; Work Item or active correction operation | owner or Diligence |
| **Resolved** | Correction applied; Evidence collected; awaiting independent verification | owner or Diligence; requires evidence filled |
| **Verified** | Independent verification completed; condition confirmed as resolved; verification Evidence present | Diligence (independent verification) |
| **Closed** | Formally closed with complete trail; no further action required | Diligence (after Verified or administrative decision) |
| **Waived** | Active approved Waiver; block suspended per policy; Finding remains visible | Documented Waiver process |

### Special cases

**Reopening:** A Closed Finding can be reopened if the condition recurs. The recurrence must be documented as a new event in the trail — does NOT overwrite the historical resolution. Create new Finding for new occurrence if context has changed significantly.

**Expired Waiver:** When a Waiver expires, the Finding automatically returns to Acknowledged status (or Open, if Acknowledged never occurred). A new decision is needed — the system does not automatically renew Waivers.

**Remediation failure:** If the Remediation was executed but the condition persists, the Finding returns from Resolved to In Remediation. The negative verification Evidence must be recorded.

**False positive / Invalid Finding:** See section below. The Finding is not deleted — it is classified with an invalidity type.

**Severity change:** Always recorded in the trail with justification. Severity can increase (new impact evidence) or decrease (evidence of partial mitigation).

**Owner change:** Recorded in the trail with reason. The previous owner remains in history.

## Subjects

Every Finding must identify what was affected. A Finding without subject is untraceable and unresolvable.

### Subject types

| Type | Examples |
|---|---|
| **Artifact** | OBC, BDD Feature, Reliability Plan, Business Signal, Business Intent |
| **Work Item** | GitHub Issue #57, GitHub Issue #312 |
| **Pull Request** | PR #42 |
| **Release** | Release v2.1.0, Release Trail entry |
| **Project** | GitHub Project "ProdOps — payments-api" |
| **View** | View "Delivery" in GitHub Project |
| **Field** | Field "Operation" in GitHub Project |
| **Label** | Label "artifact-type:local-obc" |
| **Workflow** | GitHub Actions workflow |
| **Repository** | Repository payments-api |
| **Workspace** | Complete GitHub Workspace |
| **Capability** | Capability "Readiness Verification" |
| **Journey** | Delivery journey, Diligence journey |
| **Document** | `framework/glossary.md`, `framework/ontology.md` |
| **Link** | Specific link in a document |
| **Configuration** | GitHub Project configuration, automation configuration |

### Structure of each subject

```
subject:
  type: <type from the list above>
  reference: <stable reference: URI, path, slug or ID>
  system: <source system: knowledge-space, github, external>
  classification: primary | related
```

## Finding deduplication

### Update existing Finding when:

- Same Check + same subject + same condition + same scope detected again
- Existing Finding is in state: Open, Acknowledged or In Remediation

When updating: add to trail — `last_detected_at`, occurrence count, updated impact if changed, new Evidence referenced.

### Create new Finding when:

- Different subject
- Different violated rule
- Different root cause
- Independent scope
- Previous Finding is Closed and condition represents relevant recurrence with new context

### Document recurrence

Never automatically reopen a historical Finding without preserving the new event. The recurrence is recorded in the trail of the existing Finding (if reopened) or creates a new Finding with reference to the previous (if Closed and context significantly different).

## False positive and invalid Finding

A Finding can be classified as invalid without being deleted. **Findings are never deleted.**

### Types of invalidity

| Type | When to use |
|---|---|
| **False Positive** | The detected condition does not represent a real divergence; the Check evaluated incorrectly |
| **Duplicate** | This Finding describes the same condition as a previously recorded Finding |
| **Invalid Rule** | The rule that generated the Finding is incorrect or inapplicable to the context |
| **Insufficient Evidence** | The collected Evidence is insufficient to confirm that the condition exists |
| **Superseded** | A change in the work system made this condition irrelevant |

### What to record when invalidating

- Classification of the invalidity type
- Detailed justification
- Responsible party for the classification
- Evidence supporting the invalidity
- Classification date
- Reference to the substitute Finding (if Duplicate)

**A false positive can reveal a problem in the Check.** When a False Positive is identified, verify if the Check definition or implementation needs to be corrected. In that case, it is possible to relate a Remediation to the Check itself.

## Blocking policy

A Finding can block work system operations when the following conditions are simultaneously satisfied:

| Criterion | Description |
|---|---|
| `blocking: true` in the Check | The Check is marked as blocking in its definition |
| Canonical normative source | There is a document defining the violated rule |
| Confirmed condition | The condition was verified (Fail result, not just Warning or Indeterminate) |
| Sufficient Evidence | Adequate Evidence was collected to support the blocking |
| Compatible severity | Checks with Info result never block |
| Resolution instruction | There is a documented path to resolve the block |
| Owner or escalation | There is an identified responsible party for resolution |

**A valid Waiver can suspend the block** when the Check policy allows (i.e., when `waiver_allowed: true` or not declared). Some Checks can declare `waiver_allowed: false` — in these cases, no Waiver suspends the block.

Severity Critical **does not** automatically imply impossibility of Waiver. The `waiver_allowed: false` declaration in the Check rule is what makes the Waiver impossible.

## Integration with cycles

### diligence-sync

| Phase | Use of Finding |
|---|---|
| **Capture** | May create Finding if capture reveals divergence (e.g., OBC without canonical trigger) |
| **Attach** | Relates Work Items to existing Findings |
| **Promote** | Executes Readiness Checks; blocking Findings prevent promotion |
| **Close** | Verifies related Finding; updates to Verified/Closed if condition resolved |

### diligence-async

| Phase | Use of Finding |
|---|---|
| **Scan** | Executes Checks; prepares detection Evidence |
| **Flag** | Creates Finding (if new) or updates existing Finding (if recurrence) |
| **Repair** | Executes Remediation; updates Finding to In Remediation or Resolved |

### Workspace Reconciliation

| Step | Use of Finding |
|---|---|
| **Inspect** | Produces structural Evidence; may reveal Finding (recorded on return to calling cycle) |
| **Reconcile** | Executes authorized Remediation |
| **Verify** | Produces verification Evidence; updates Finding to Verified when condition resolved |

## Five mandatory examples

### Example 1 — Work Item without Artifact ID

**Context:** diligence-async Scan detects Work Item with missing required field.

1. Traceability Check (DIL-TRC-001) executes during Scan phase
2. High Finding created: "Work Item #57 does not have a valid Artifact ID" (FND-2026-0001)
   - `subjects`: `[{type: Work Item, reference: github://issues/57, system: github}]`
   - `source_of_truth`: `prodops/framework/execution-mapping/work-item-schema.md`
3. Evidence EVD-2026-0001 collected: output of `gh issue view 57 --json body,labels` showing absent field
4. Remediation RMD-2026-0001 proposed and approved: update Work Item fields with artifact reference
5. Remediation Work Item created; fields corrected
6. Check (DIL-TRC-001) executed again → Pass
7. Evidence EVD-2026-0002 collected: `gh issue view 57 --json body,labels` showing filled field
8. Finding updated → Resolved → Verified → Closed

**Lesson:** Finding lives in Knowledge Space; the correction Work Item lives in Execution Space; they are distinct entities.

---

### Example 2 — Passive Business Signal without Issue

**Context:** diligence-async Scan evaluates Business Signals in tracking list.

1. Check evaluates: "Does Business Signal #BS-042 have an active operation without a trackable Work Item?"
2. Result: **Not Applicable** — passive signal, no authorized active investigation, no ongoing operation
3. No Finding created
4. Trail records: "BS-042 evaluated on 2026-07-23; absence of Work Item is legitimate; no active operation identified"

**Lesson:** Absence of Issue is not an automatic divergence. Check returning Not Applicable does not generate Finding.

---

### Example 3 — Required field removed from GitHub Project

**Context:** diligence-async Scan detects workspace drift.

1. Structural Check (DIL-STR-007) executes: "Does field 'Operation' exist in the GitHub Project?"
2. Medium Finding created (FND-2026-0002): "Required field 'Operation' absent from GitHub Project 'ProdOps — payments-api'"
   - `subjects`: `[{type: Field, reference: github://projects/payments-api/fields/Operation, system: github}]`
3. Evidence EVD-2026-0003 collected: output of `gh project field-list` before and after showing absence
4. Workspace Reconciliation invoked as Remediation (RMD-2026-0002): restore field following Canonical Specification
5. Reconcile executes; field restored
6. Evidence EVD-2026-0004 collected: output of `gh project field-list` confirming field present
7. Check (DIL-STR-007) executed again → Pass
8. Finding → Verified → Closed

**Lesson:** Workspace drift is handled by Workspace Reconciliation as Remediation; before and after Evidence documents the condition and resolution.

---

### Example 4 — Reliability Plan absent when required

**Context:** diligence-sync Promote detects unsatisfied precondition.

1. Blocking Readiness Check (DIL-OPS-003) executes: "Does Reliability Plan exist for item with financial movement?"
2. OBC "payment-gateway" — financial movement identified; Reliability Plan absent
3. High Finding created (FND-2026-0003): "Reliability Plan absent for OBC payment-gateway with financial movement"
   - `blocking`: true (Check is blocking)
   - `source_of_truth`: `prodops/framework/backlogs.md` (section: conditional gate)
4. Iteration Plan promotion blocked
5. Evidence EVD-2026-0005 collected: OBC file + Assessment decision referencing need
6. Remediation RMD-2026-0003: create Reliability Plan after authorized decision by Assessment
7. Reliability Plan created and reviewed
8. Evidence EVD-2026-0006: created Reliability Plan file + documented review
9. Check (DIL-OPS-003) executed again → Pass
10. Promotion block suspended; promotion completed
11. Finding → Verified → Closed

**Lesson:** Blocking Finding prevents advancement; Remediation resolves the condition; Check re-executed confirms resolution before releasing.

---

### Example 5 — Temporary Waiver

**Context:** Acknowledged Finding; Remediation cannot be completed before the Release.

1. High Finding acknowledged (FND-2026-0004): "Circular dependency between OBC 'analytics' and OBC 'reporting'"
   - Status: Acknowledged
2. Team evaluates: refactoring needed, but cannot be completed before Release v2.1.0 (10 days)
3. Product Owner requests Waiver; Tech Lead approves
4. Waiver created (WVR-2026-0001):
   - `finding_id`: FND-2026-0004
   - `reason`: "Circular dependency refactoring cannot be completed before Release v2.1.0; risk mitigated by manual integration tests"
   - `expires_at`: 2026-08-07 (14 days)
   - `compensating_controls`: ["manual integration tests before each deploy", "impact review by Tech Lead"]
   - `approved_by`: Tech Lead
5. Finding → Waived; promotion block suspended
6. Finding remains visible and trackable with Waived status
7. Waiver expires on 2026-08-07 → Finding returns to Acknowledged
8. New decision needed: Remediation completed (if possible) or new Waiver with new justification

**Lesson:** Waiver does not eliminate the Finding; does not alter the rule; does not declare the condition correct; the Finding remains trackable; expired Waiver requires a new conscious decision.
