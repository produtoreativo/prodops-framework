# Check — Canonical Definition

## Definition

> **A Check is a declarative, reproducible and verifiable rule used by Diligence to evaluate a condition of the work system.**

A Check defines WHAT must be evaluated and what result is expected. It does not define when or who evaluates — that is determined by the Diligence cycles and the execution mode. A well-defined Check produces consistent results regardless of who executes it or when.

---

## ID format

```
DIL-[CATEGORY]-NNN
```

- `DIL`: immutable Diligence prefix
- `[CATEGORY]`: 3-letter abbreviation of the Finding category that the Check can generate:
  - `ART` — Artifact
  - `BKL` — Backlog
  - `WIT` — Work Item
  - `EXM` — Execution Mapping
  - `DOC` — Documentation
  - `WSP` — Workspace
  - `RDY` — Readiness
  - `REL` — Reliability
  - `OBS` — Observability
  - `SEC` — Security
  - `RLS` — Release
  - `EVD` — Evidence
  - `GOV` — Governance
  - `TRC` — Traceability
  - `OPS` — Operational
  - `STR` — Structural
- `NNN`: three-digit sequential per category (001–999)

The ID is stable even when the Check implementation changes. The Check version is tracked separately in the `version` field.

Examples: `DIL-TRC-001`, `DIL-STR-007`, `DIL-OPS-003`, `DIL-RDY-002`

## Schema

| Field | Conceptual type | Cardinality | Rules and examples |
|---|---|---|---|
| `id` | string | 1 | Format DIL-CATEGORY-NNN; immutable; unique in the catalog |
| `name` | string | 1 | Human-readable name; must clearly indicate what is being verified. Ex: "Work Item has valid Artifact ID" |
| `description` | text | 1 | Complete description of what the Check evaluates, why it matters and when it is applicable |
| `dimension` | enum | 1 primary | Conceptual, Structural, Traceability, Operational or Temporal — see `finding.md` for definitions |
| `category` | enum | 1 | Same category list as Finding: Artifact, Backlog, Work Item, Execution Mapping, Documentation, Workspace, Readiness, Reliability, Observability, Security, Release, Evidence, Governance |
| `scope` | text | 1 | What the Check evaluates: specific artifacts, all active OBCs, open Work Items, GitHub Workspace, etc. |
| `rule` | text | 1 | The declarative rule: "For every X in state Y, Z must exist/contain/reference W" |
| `severity_default` | enum | 1 | Default severity of the Finding generated when the Check fails: Critical, High, Medium, Low or Info. May be adjusted by context |
| `blocking` | boolean | 1 | `true` if the Check can block state transitions; `false` if informative only. Info checks are never blocking |
| `execution_mode` | enum | 1 | Sync, Async, Manual, Event-driven or Scheduled — see section below |
| `trigger` | text | 1 | What triggers execution: specific event, cycle phase, period, request |
| `inputs` | list | 1..N | What the Check reads: files, APIs, Work Items, artifact states |
| `source_of_truth` | string | 1 | Canonical reference that supports the rule. Ex: `prodops/framework/execution-mapping/work-item-schema.md` |
| `expected_condition` | text | 1 | Describes what constitutes a Pass result — system state when everything is correct |
| `failure_condition` | text | 1 | Describes what constitutes a Fail result — system state that violates the rule |
| `evidence_required` | text | 1 | What evidence must be collected: what to capture, from where, in what format |
| `automation_level` | enum | 1 | Current automation level: Manual, Automated, Partial |
| `owner` | string | 1 | Role responsible for the Check definition and maintenance |
| `version` | string | 1 | Semantic version of the Check rule. Ex: `1.0.0`, `1.2.1`. Changes when the rule changes — not when the implementation changes |
| `waiver_allowed` | boolean | 0..1 | If absent, assumes `true`. When `false`, no Waiver can suspend the block generated by this Check |

## Check type taxonomy

A Check has a primary type and may have optional secondary types.

| Type | Definition | Rule example |
|---|---|---|
| **Presence** | Verifies mandatory existence of something | "BDD Feature must exist for OBC in Iteration Plan" |
| **Absence** | Verifies absence of something that should not be present | "Closed Work Item must not have open active operations referencing it" |
| **Validity** | Verifies that a value or reference is valid and exists | "artifact_id in Work Item must reference an artifact that exists in the repository" |
| **Consistency** | Compares two or more sources or states | "OBC state in the Markdown file must be consistent with the state in the GitHub Project Field" |
| **Completeness** | Verifies that required fields are filled with acceptable values | "Work Item must have artifact_type, artifact_id, operation and journey filled" |
| **Traceability** | Verifies relationship chain between entities | "Every OBC in In Delivery must have at least one open implementation Work Item" |
| **Readiness** | Verifies preconditions for advancement | "OBC in Iteration Plan must have BDD Feature Committed" |
| **Freshness** | Verifies temporal validity of information | "Waiver must not be expired for Finding with Waived status" |
| **Conformance** | Verifies adherence to schema or configuration | "GitHub Project must have all canonical fields defined in github-workspace.md" |
| **Outcome** | Verifies that Evidence supports the declared result | "Resolved Finding must have resolution Evidence collected" |

## Execution modes

| Mode | Definition | Triggered by | Example |
|---|---|---|---|
| **Sync** | Executed within a transition or ongoing operation | diligence-sync cycle phase | Readiness Check in the Promote step |
| **Async** | Executed outside the main transaction | diligence-async periodic scan | Work Item completeness Check in Scan |
| **Manual** | Executed on explicit request | Human request or bootstrap | Vocabulary audit in normative documents |
| **Event-driven** | Triggered by technical or operational event | PR opened, OBC state changed, document edited | Traceability Check triggered by PR |
| **Scheduled** | Executed periodically at defined interval | Scheduler | Weekly Check for expired Waivers |

## Check results

| Result | Meaning | Generates Finding? |
|---|---|---|
| **Pass** | Condition satisfied; system conforms to rule | No |
| **Fail** | Confirmed violation; condition not satisfied | Yes — Finding with Check's `severity_default` |
| **Warning** | Relevant condition detected without blocking violation | May generate Finding with Info or Low severity; depends on Check definition |
| **Not Applicable** | The rule does not apply to the evaluated context | No |
| **Indeterminate** | Insufficient evidence or inadequate information to conclude | May generate Governance Finding if recurrent; requires escalation |
| **Error** | The Check could not execute correctly | May generate operational Finding about Diligence mechanism failure; does NOT generate Finding for the original rule |

### Rules about results

- **Indeterminate ≠ Pass.** Indeterminate means there is not sufficient evidence to confirm conformance — it is not confirmation that everything is correct.
- **Error does NOT automatically generate a Finding for the original rule.** If the Check failed to execute, one cannot conclude that the rule was violated. Error may generate a separate operational Finding about the Diligence mechanism failure.
- **Warning does NOT imply Fail.** A Check that returns Warning identified something worthy of attention, but without a blocking rule violation.
- **Not Applicable is a valid and explicit result.** Do not record as Pass or as absence of evaluation — record as Not Applicable with justification.

## Blocking rule

A Check marked with `blocking: true` can prevent state transitions when it returns Fail.

For the block to be valid, ALL criteria below must be simultaneously satisfied:

1. `blocking: true` declared in the Check definition
2. A canonical `source_of_truth` is identified — the rule has documented normative basis
3. Result is Fail (not Warning, Indeterminate or Error)
4. Sufficient Evidence was collected to support the Fail result
5. `failure_condition` is documented — there is instruction on how to resolve
6. Owner or escalation target identified

**Checks with Info result never block**, regardless of `blocking: true`.

**Waiver can suspend the block** when `waiver_allowed: true` (or not declared) and the Waiver satisfies all validity criteria.

**`waiver_allowed: false`** makes the block unsuspendable by Waiver. This declaration should be used judiciously — only for cases where the condition represents risk that cannot be managed by temporary acceptance (e.g., deliberate irreversible loss of traceability, confirmed legal violation, promotion without mandatory documented approval in a regulatory context).
